# 0009 — Adaptive multi-background theme system

## Status

Accepted on 2026-07-29.

## Context

Codex Assistant ships multiple bright, dark, saturated, muted, simple, and detailed
backgrounds. A single fixed opacity and blur recipe cannot keep the official Codex
interface readable across that catalog. Per-image CSS overrides would also make the
theme engine difficult to review and unsafe to extend.

The theme engine must continue to preserve official content, semantic SVG fills,
primary actions, hit targets, scrolling, keyboard behavior, and sensitive-page
fail-closed behavior.

## Decision

Every theme pack may carry one `adaptation` profile:

- `luminance`: perceived average brightness from 0 to 100.
- `complexity`: local edge density and luminance variance from 0 to 100.
- `saturation`: average HSV-style saturation from 0 to 100.

Bundled theme builds calculate these values from a 64 × 64 decoded sample. Local
PNG, JPEG, and WebP imports calculate the same profile on-device. Older local
manifests remain valid and use a conservative fallback profile.

The runtime emits one design system for every background:

1. **Surface-0 / atmosphere** — one fixed, non-interactive background image plus
   one adaptive regional scrim.
2. **Surface-1 / application frame** — sidebar, header, and output panel.
3. **Surface-2 / structured information** — messages, plans, sources, tool calls,
   reasoning and status records.
4. **Surface-3 / interaction** — composer, model selector, buttons, dropdowns,
   chips, focus and open states.

All colors, opacity, blur, shadow, radius, text, and status accents are emitted as
CSS custom properties. Bright or detailed images receive stronger overlays and
more opaque surfaces. Dark images retain lighter separation without turning the
whole application black. Highly saturated images are gently desaturated only in
the background layer.

Running, success, warning, error, and informational records share one structured
status surface and use distinct left-edge accents. The rules do not change their
content, disclosure behavior, or native event handling.

## Performance budget

- Exactly one decoded theme background is loaded.
- The background itself is never blurred.
- Main reading and nested status cards do not use `backdrop-filter`.
- The normal task page may expose at most three visible expensive glass layers:
  sidebar, output panel, and composer.
- Transitions use transform, opacity, background color, border color, or shadow
  only, and reduced-motion mode collapses them to one frame.

## Verification

The test contract covers all bundled themes at 1920 × 1080, 2560 × 1440,
3440 × 1440, windowed layouts, and 100%–200% scale. It verifies:

- adaptive profiles and required tokens;
- background sizing, focal position, no tiling, and no input capture;
- readable surfaces and bounded live glass layers;
- state colors and structured status spacing;
- preserved text, images, semantic SVG fills, primary actions, focus, scrolling,
  menus, dialogs, dropdowns, links, and composer submission;
- exact restore, route continuity, local imports, sensitive pages, and unknown
  builds;
- rejection of deliberate overlay, semantic recolor, and invisible-focus
  regressions.

## Consequences

Adding a bundled theme requires valid adaptation metadata generated by the build
pipeline. New UI selectors must map to an existing surface level instead of
inventing component-local opacity values. Any increase in the live blur budget or
semantic content override requires a new reviewed architectural decision.
